# Software Engineering Philosophy

Software Engineering at Google（Abseil / O'Reilly）に基づく
ソフトウェア工学の哲学と実践原則。

参考文献:
- [Software Engineering at Google](https://abseil.io/resources/swe-book/html/toc.html)

## 根幹の哲学: プログラミングとソフトウェアエンジニアリングの違い

> Software engineering is programming integrated over time.

- プログラミングは「動くコードを書くこと」
- ソフトウェアエンジニアリングは「時間の経過に耐えるコードを書くこと」
- コードは書いた瞬間から陳腐化が始まる。依存ライブラリの更新、OS の変更、チームメンバーの入れ替わり
- 「このコードはあとどれくらい生きるか？」が設計判断の出発点

## Time and Change（時間と変化）

### Hyrum's Law

> With a sufficient number of users of an API, all observable behaviors of your system will be depended on by somebody.

- API の利用者が十分に多ければ、ドキュメントに書いていない振る舞いにも誰かが依存する
- 「仕様ではない」は「変更しても安全」を意味しない
- 変更のコストはユーザー数に比例して増大する
- 対策: 明確なインターフェース契約、段階的な非推奨化、自動化されたテスト

### 変更を前提とした設計

- 「何も変えない」は選択肢ではない。依存関係は常に変化する
- 変更のコストを下げる投資（テスト、CI、自動リファクタリング）は長期的に回収できる
- 「Shifting Left」: 問題を開発プロセスの早い段階で発見するほど修正コストが低い

## Scale and Efficiency（スケールと効率）

### スケールしないポリシー

- 「全員がすべてのコードを読む」はスケールしない
- 「変更のたびに手動テスト」はスケールしない
- 「1人の専門家に依存する」はスケールしない（Bus Factor = 1）

### スケールするポリシー

- 自動化されたテストとCI
- コードオーナーシップとレビュープロセス
- 標準化されたスタイルガイドとツール
- ドキュメントの正規化（Canonical Source of Information）

## Trade-offs and Costs（トレードオフとコスト）

すべての技術的判断はトレードオフ。以下の入力を考慮する:

- 金銭的コスト（インフラ、ライセンス）
- 時間的コスト（開発工数、メンテナンス工数）
- 機会費用（この作業をする代わりにできなかったこと）
- 社会的コスト（チームの士気、採用への影響）
- 安全性コスト（セキュリティリスク、データ損失リスク）

「正しい判断」は存在しない。「その時点で最善のトレードオフ」があるだけ。
判断を記録し（ADR）、状況が変わったら見直す。

## Culture（文化）

### チームワークの三本柱

1. Humility（謙虚さ）: 自分は完璧ではない。常に学ぶ姿勢
2. Respect（尊重）: 同僚の能力と貢献を認める
3. Trust（信頼）: 他者が正しいことをすると信じる

- この3つが欠けると、コードレビューは攻撃になり、Postmortem は責任追及になる
- 「Googley」であること = HRT を実践すること

### Blame-free Post-Mortem Culture

- 失敗は学習の機会。個人を責めない
- 「壊れた窓」を放置しない。問題を見つけたら声を上げる
- 心理的安全性がなければ、問題は隠蔽される

### Knowledge Sharing（知識共有）

- 知識は個人に閉じ込めない。ドキュメント、Tech Talk、コードレビューで共有する
- 「質問すること」を奨励する。質問は無知の表れではなく、学習の表れ
- Canonical Source of Information を確立する。同じ質問に何度も答えない仕組み

## Processes（プロセス）

### Style Guide と Rules

- コードスタイルは統一する。議論のコストを減らし、可読性を上げる
- ルールは「なぜそのルールが必要か」を説明できること
- ルールは変更可能。状況が変わったら見直す
- 自動フォーマッター、Linter で機械的に強制する

### Code Review

- すべての変更はレビューを通す。例外なし
- レビューの目的: 正確性、理解容易性、一貫性、知識共有
- 小さな変更を頻繁にレビューする。巨大な変更はレビューの質が下がる
- レビューコメントは丁寧かつプロフェッショナルに

### Documentation

- ドキュメントはコードと同じ品質基準で管理する
- ドキュメントの種類: リファレンス、設計ドキュメント、チュートリアル、概念説明
- 「誰が読むか」を意識して書く（Audience）
- 古くなったドキュメントは削除する。誤ったドキュメントはドキュメントがないより悪い

## Testing（テスト）

### テストの価値

- テストは「変更を安全にする」ためにある
- テストがなければ、リファクタリングは恐怖を伴う
- テストスイートは「生きたドキュメント」。コードの振る舞いを定義する

### テストサイズとスコープ

- Small / Medium / Large のサイズ分類（`testing-philosophy.md` と整合）
- テストスコープ: Unit（狭い）→ Integration（中間）→ E2E（広い）
- テストピラミッド: Small を最も多く、Large を最も少なく
- Beyoncé Rule: "If you liked it, you should have put a test on it"

### テストダブル

- Real Implementation > Fake > Stub > Mock の優先順位
- State Testing > Interaction Testing を優先する
- 過度なモックはテストの信頼性を下げる

## Deprecation（非推奨化）

- 使われなくなったシステム/API は積極的に非推奨化・削除する
- Advisory Deprecation（推奨）と Compulsory Deprecation（強制）を使い分ける
- 非推奨化のプロセス: 告知 → 移行期間 → 削除
- 「いつか消す」は「永遠に残る」と同義。期限を設定する

## CI / CD

### Continuous Integration

- すべての変更は自動テストを通す
- テストは高速であること。遅いテストは実行されなくなる
- Hermetic Testing: テスト環境は外部依存から隔離する
- テストの失敗は即座に修正する。壊れたテストを放置しない

### Continuous Delivery

- リリースの頻度を上げる。小さなリリースはリスクが小さい
- Feature Flag で未完成機能を隠す
- Canary リリースで段階的にロールアウトする
- データ駆動の意思決定。リリースの影響をメトリクスで評価する

## Large-Scale Changes（大規模変更）

- 大規模変更は避けられない（ライブラリ更新、API 変更、セキュリティ修正）
- 自動化ツールで変更を生成し、コードオーナーにレビューを依頼する
- 変更を小さなチャンクに分割し、段階的に適用する
- テストで安全性を担保する。手動確認はスケールしない

## Compute as a Service

- インフラを抽象化し、開発者がビジネスロジックに集中できるようにする
- コンテナ化でマルチテナンシーと効率的なリソース利用を実現する
- 障害を前提とした設計（Architecting for Failure）
- Batch と Serving を区別し、適切なコンピュートモデルを選択する

## アンチパターン

- 「動いているから触らない」（技術的負債の蓄積）
- Bus Factor = 1（知識が1人に集中）
- テストなしのリファクタリング（恐怖駆動開発）
- ドキュメントを書かない（暗黙知への依存）
- 巨大な変更を一度にリリースする（リスクの集中）
- 非推奨化を先延ばしにする（レガシーの永続化）
- 「自分のコード」意識（コードは個人のものではなくチームのもの）
