## 根幹の哲学

### Monitoring は行動であり、Observability はシステムの属性である

- Monitoring: システムの状態を収集・処理・集約・表示する行動
- Observability: システムが Monitoring を可能にする属性。Observable なシステムほど良く監視できる
- Monitoring の目的は 5 つ: アラート、調査・診断、可視化、トレンド分析、変更前後の比較

### アラートの哲学

ページャーを鳴らすことは、エンジニアの時間を消費する高コストな行為である。

- すべてのアラートは Actionable でなければならない。対応不要なアラートはノイズ
- すべてのアラートは Intelligence を要求すべき。ロボット的な対応で済むならアラートではなく自動化する
- すべてのアラートは Urgency を持つべき。朝まで待てるなら Ticket にする
- アラートは Novel な問題を通知すべき。既知の問題の繰り返しなら根本原因を修正する

### アラート設計の 5 つの問い

新しいアラートを作成・レビューする際に必ず問う:

1. このルールは、他に検知手段がない、緊急で、対応可能で、ユーザーに影響がある状態を検知するか？
2. このアラートを「良性」と判断して無視することがあるか？ あるなら、そのシナリオを排除できないか？
3. このアラートはユーザーが実際に悪影響を受けていることを確実に示すか？ ドレイン中やテスト環境はフィルタされているか？
4. このアラートに対して取れるアクションがあるか？ そのアクションは緊急か、朝まで待てるか？ 自動化できないか？
5. 同じ問題で他の人もページされていないか？ 重複アラートになっていないか？

## Monitoring の基本原則

### Symptom（症状）vs Cause（原因）

| 症状 | 原因 |
|------|------|
| HTTP 500 が増加している | DB が接続を拒否している |
| レスポンスが遅い | CPU が過負荷 / ネットワーク障害 |
| ユーザーがコンテンツを受信できない | CDN の設定ミス |

- アラートは Symptom（症状）に基づいて発火させる。Cause（原因）はデバッグ時に調査する
- 「何が壊れているか」と「なぜ壊れているか」を明確に区別する
- Symptom ベースのアラートは、原因が予想外でも検知できる

### Black-Box vs White-Box Monitoring

| 種類 | 特徴 | 用途 |
|------|------|------|
| Black-Box | 外部からユーザー視点で監視。現在進行中の問題を検知 | ページング（即時対応） |
| White-Box | 内部メトリクス・ログを監視。潜在的な問題を検知 | デバッグ、予兆検知 |

- ページングには Black-Box を優先する（実際にユーザーに影響が出ている状態のみ通知）
- White-Box はデバッグと予兆検知に使う（リトライで隠れた障害、リソース枯渇の予兆）
- 両方を組み合わせる。Black-Box だけでは「まだ起きていないが差し迫った問題」を検知できない

### Four Golden Signals

ユーザー向けシステムで最低限監視すべき 4 つのシグナル:

| シグナル | 説明 | 測定例 |
|----------|------|--------|
| Latency | リクエスト処理時間。成功リクエストと失敗リクエストのレイテンシを区別する | p50, p95, p99 レスポンスタイム |
| Traffic | システムへの需要量 | HTTP requests/sec, concurrent sessions |
| Errors | 失敗リクエストの割合。明示的（5xx）、暗黙的（200 だが不正な内容）、ポリシー的（SLO 超過） | エラー率 (%) |
| Saturation | システムの「満杯度」。リソースの制約に最も近い指標 | CPU 使用率, メモリ使用率, ディスク使用率, Queue 深度 |

- この 4 つを監視し、問題があればページすれば、最低限のカバレッジは確保できる
- Saturation は予測も含む（「4時間後にディスクが満杯になる」）
- Latency の p99 は Saturation の先行指標になることが多い

### テールレイテンシに注意する

- 平均値だけを見ると、テールレイテンシの問題を見逃す
- p99 の 1 バックエンドが、フロントエンドの p50 になりうる（Fan-out の場合）
- ヒストグラムバケットでレイテンシ分布を収集する（指数的な境界: 10ms, 30ms, 100ms, 300ms, ...）

## SLO ベースのアラート

### なぜ SLO ベースか

- 従来の静的閾値アラート（CPU > 80%, エラー率 > 5%）は、ユーザー影響と直接相関しない
- SLO ベースのアラートは「Error Budget がどれだけ消費されているか」に基づく
- Error Budget の消費速度（Burn Rate）でアラートすることで、Precision と Recall のバランスを取る

### Burn Rate の概念

```
Burn Rate = 実際のエラー率 / SLO が許容するエラー率

例: SLO 99.9%（許容エラー率 0.1%）で実際のエラー率が 1% の場合
    Burn Rate = 1% / 0.1% = 10x
    → 通常の 10 倍の速度で Error Budget を消費中
```

| Burn Rate | エラー率（SLO 99.9%） | Budget 枯渇までの時間 |
|-----------|----------------------|---------------------|
| 1x        | 0.1%                 | 30 日               |
| 2x        | 0.2%                 | 15 日               |
| 10x       | 1%                   | 3 日                |
| 1000x     | 100%                 | 43 分               |

### Multi-Window, Multi-Burn-Rate アラート（推奨）

SRE Workbook が推奨する最も実践的なアラート手法。
Long Window で Budget 消費を検知し、Short Window で「今も消費中か」を確認する。

#### 推奨パラメータ（SLO 99.9% の場合）

| 重大度 | Long Window | Short Window | Burn Rate | Budget 消費量 | 通知方法 |
|--------|-------------|--------------|-----------|--------------|---------|
| Page   | 1 時間      | 5 分         | 14.4x     | 2%           | PagerDuty / Slack 即時 |
| Page   | 6 時間      | 30 分        | 6x        | 5%           | PagerDuty / Slack 即時 |
| Ticket | 3 日        | 6 時間       | 1x        | 10%          | Ticket 作成 |

```
# Page アラート（高速消費 OR 中速消費）
(
  error_rate_1h > 14.4 * (1 - SLO)
  AND error_rate_5m > 14.4 * (1 - SLO)
)
OR
(
  error_rate_6h > 6 * (1 - SLO)
  AND error_rate_30m > 6 * (1 - SLO)
)

# Ticket アラート（低速消費）
(
  error_rate_3d > 1 * (1 - SLO)
  AND error_rate_6h > 1 * (1 - SLO)
)
```

- Short Window は Long Window の 1/12 を目安にする
- Short Window により、問題解消後のリセット時間が短くなる（1時間 → 5分）
- 複数条件が同時に true になる場合のアラート抑制を実装する

## 新規サービスの初期アラート設計

新しいサービスを立ち上げる際の、Day 1 から設定すべきアラートのベースライン。

### Phase 1: 最低限（Day 1）

SLO が未策定でも、以下は即座に設定する:

| アラート | 条件 | 重大度 |
|---------|------|--------|
| サービスダウン | ヘルスチェック失敗が N 分継続 | Page |
| 高エラー率 | 5xx 率 > 5% が 5 分継続 | Page |
| 高レイテンシ | p99 > 閾値 が 5 分継続 | Page |
| リソース枯渇予兆 | CPU > 90% / Memory > 85% / Disk > 80% | Ticket |
| 証明書期限 | SSL 証明書の有効期限 < 30 日 | Ticket |

- 閾値は仮の値でよい。2 週間のデータを収集してから調整する
- 「何もアラートがない」状態でサービスを運用してはならない

### Phase 2: SLO ベース（2〜4 週間後）

トラフィックデータが蓄積されたら:

1. CUJ を特定し、SLI/SLO を策定する（`sre-philosophy.md` 参照）
2. Phase 1 の静的閾値アラートを SLO ベースの Burn Rate アラートに置き換える
3. Error Budget Policy を策定し、関係者と合意する

### Phase 3: 成熟（1〜3 ヶ月後）

運用経験に基づいて:

1. 依存サービスの SLI を監視に追加する
2. カスタム業務メトリクスのアラートを追加する
3. Runbook を整備し、アラートとリンクする
4. アラートの Precision / Recall を振り返り、チューニングする

## カスタムアラート設計のルール

### アプリケーション仕様に沿ったアラート

SLO ベースのアラートだけでは捕捉できない、業務固有の異常を検知するアラート。

#### 設計の原則

- ユーザー影響に直結する業務メトリクスを特定する
- 「正常な状態」を定義してから「異常な状態」を定義する
- 静的閾値よりも、ベースラインからの乖離（異常検知）を優先する
- アラートには必ず Runbook URL を含める

#### カスタムアラートの例

| ドメイン | メトリクス | 条件 | 理由 |
|---------|-----------|------|------|
| 決済 | 決済成功率 | < 95% が 5 分継続 | 収益に直結 |
| 認証 | ログイン失敗率 | > 10% が 10 分継続 | ユーザーがサービスを利用できない |
| Queue | メッセージ滞留数 | > 閾値 が 15 分継続 | 処理遅延がユーザーに影響 |
| Batch | ジョブ実行時間 | 通常の 2 倍を超過 | SLA 違反の予兆 |
| データ同期 | 最終同期からの経過時間 | > 閾値 | データ鮮度の劣化 |
| 外部 API | 依存サービスのエラー率 | > 閾値 が 5 分継続 | 自サービスへの波及 |

### 依存サービスの監視

- すべての直接依存に対して、リクエスト/レスポンスサイズ、レイテンシ、レスポンスコードを監視する
- Four Golden Signals を依存サービスごとに収集する
- RPC クライアントライブラリレベルで計装し、新しい依存を追加したら自動的に監視される設計にする

### リソース監視

すべてのサービスで以下のリソースを監視する:

| リソース | アラート条件 | 備考 |
|---------|------------|------|
| CPU | > 90% 持続 | Saturation の先行指標 |
| Memory | > 85% 持続 | OOM Killer の予兆 |
| Disk | > 80% 持続 / 増加率から枯渇予測 | 「4時間後に満杯」も検知 |
| File Descriptors | > 80% of limit | 接続数の上限 |
| Thread Pool | Active > 80% of max | 処理能力の上限 |
| Queue Depth | > 閾値 持続 | 処理遅延の予兆 |

言語固有のリソース:
- Go: goroutine 数の異常増加
- Java: Heap / Metaspace サイズ、GC Pause Time

### 変更の監視

障害の多くは変更に起因する。以下を監視し、障害との相関を取れるようにする:

- バイナリバージョン（デプロイ）
- Feature Flag の状態
- 動的設定の変更タイムスタンプ
- インフラ変更（スケーリングイベント、設定変更）

## アラートの運用ルール

### アラートの分類と通知先

| 重大度 | 説明 | 通知先 | 対応時間 |
|--------|------|--------|---------|
| Page（Critical） | ユーザーに影響が出ている、または差し迫っている | PagerDuty → On-Call | 即時（5分以内に Acknowledge） |
| Ticket（Warning） | 対応が必要だが、即時ではない | Ticket 作成 + Slack 通知 | 翌営業日 |
| Informational | 参考情報。ダッシュボードに表示 | ダッシュボードのみ | 対応不要 |

- Email アラートは使わない。ノイズに埋もれて無視される
- Page は 1 シフトあたり 2 件以下を目標にする。超えたらアラートのチューニングか根本原因の修正が必要

### Runbook

すべての Page アラートに Runbook を紐付ける。

```markdown
# Runbook: {アラート名}

## 概要
このアラートが発火する条件と、ユーザーへの影響。

## 確認手順
1. ダッシュボード {URL} を確認する
2. {具体的な確認コマンドやクエリ}

## 対応手順
1. {最も一般的な原因と対応}
2. {次に一般的な原因と対応}

## エスカレーション
- {エスカレーション先と条件}
```

### アラートのメンテナンス

- 四半期ごとにすべてのアラートをレビューする
- 過去 90 日間で一度も発火していないアラートは削除を検討する
- 発火したが対応不要だったアラートは閾値を調整するか削除する
- 新しい Postmortem のアクションアイテムとしてアラートを追加する
- Maintenance Window（メンテナンス期間）を設定し、計画的な作業中のノイズを抑制する

### アラートのテスト

- アラートルールはコードとして管理する（Infrastructure as Code）
- 合成データでアラートの発火条件をテストする
- アラートが正しい宛先にルーティングされることを検証する
- 長期間発火していないアラートは、定期的に手動でテストする

## Monitoring のアンチパターン

### Practical Monitoring のアンチパターン

| アンチパターン | 問題 | 対策 |
|---------------|------|------|
| Tool Obsession | ツール選定に時間をかけすぎて、監視の目的を見失う | 目的から逆算してツールを選ぶ |
| Monitoring-as-a-Job | 監視を専任の仕事にする | 全エンジニアが監視に責任を持つ |
| Checkbox Monitoring | 「監視している」というチェックボックスを埋めるだけ | 「Working」の定義を明確にしてから監視する |
| Using Monitoring as a Crutch | 監視で問題を検知する代わりに、根本原因を修正しない | 検知 → 修正のサイクルを回す |
| Manual Monitoring | 画面を見張って問題を検知する | 自動化されたアラートに置き換える |

### Google SRE のアンチパターン

| アンチパターン | 問題 | 対策 |
|---------------|------|------|
| 複雑な依存関係ルール | メンテナンスコストが高く、壊れやすい | シンプルなルールを維持する |
| Magic システム | 自動的に閾値を学習するシステムは壊れやすい | シンプルで予測可能なルールを使う |
| Email アラート | ノイズに埋もれて無視される | ダッシュボード + Ticket に置き換える |
| 原因ベースのアラート | 予想外の原因を検知できない | 症状ベースのアラートを優先する |
| 過剰なアラート | アラート疲れで本当の問題を見逃す | アラートを削減し、SLO ベースに移行する |

## Low-Traffic サービスのアラート

トラフィックが少ないサービスでは、SLO ベースのアラートが過敏になる問題がある。

- 1 リクエストの失敗が大きな Burn Rate を生む（10 req/h で 1 失敗 = 10% エラー率 = 1000x Burn Rate）
- 対策:
  1. Synthetic Traffic（合成トラフィック）を生成してシグナルを補強する
  2. 関連する小規模サービスを集約して監視する
  3. クライアント側でリトライを実装し、単発障害の影響を軽減する
  4. SLO 目標値を実態に合わせて調整する（99.9% → 99%）

## ダッシュボード設計

### 階層構造

| レベル | 対象者 | 内容 |
|--------|--------|------|
| Service Overview | 全員 | SLO 達成状況、Error Budget 残量、Four Golden Signals |
| Detailed Service | On-Call / 開発者 | 依存サービスの状態、リソース使用率、デプロイ履歴 |
| Debug | On-Call | 個別コンポーネントの詳細メトリクス、ログへのリンク |

### 設計原則

- ダッシュボードは事前に構築する。インシデント中に作らない
- 同じ種類のデータは一貫したフォーマットで表示する
- アラートからダッシュボードへのリンクを必ず含める
- 対数スケールを活用する（スパイクに埋もれた詳細を見るため）
- 不要なダッシュボードは削除する。使われていないダッシュボードはメンテナンスコスト

## 測定の解像度

| 対象 | 推奨解像度 | 理由 |
|------|-----------|------|
| CPU 使用率 | 10〜60 秒 | テールレイテンシの原因となるスパイクを検知 |
| ヘルスチェック | 30〜60 秒 | 99.9% SLO なら 1〜2 分間隔で十分 |
| ディスク使用率 | 1〜5 分 | 急激な変化は稀 |
| ビジネスメトリクス | 1〜5 分 | トレンド分析が主目的 |

- 高解像度データは内部でサンプリングし、集約して保存する（コスト最適化）
- 長期保存データは解像度を下げてよい（1分 → 5分 → 1時間）
