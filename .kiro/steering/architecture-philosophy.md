# Architecture Philosophy

言語・フレームワーク非依存のシステムアーキテクチャ決定原則。
設計判断の拠り所となる哲学と、意思決定のフレームワークを定義する。
具体的な設計パターンの選択ガイドは `system-design-patterns.md` を参照。
ソフトウェア工学的な視点は `software-engineering-philosophy.md`、SRE 視点は `sre-philosophy.md` を参照。

## 設計の最上位原則

- 変更容易性を最優先する。ソフトウェアの価値は「変更できること」にある
- 早すぎる最適化をしない。まず正しく動くものを作り、計測し、必要な箇所だけ最適化する
- 決定を遅延させる。取り返しのつかない決定（DB選定、クラウドプロバイダ等）は可能な限り遅らせ、情報が揃ってから決める
- シンプルさを追求する。複雑さはバグの温床。必要になるまで抽象化しない（YAGNI）

## Clean Architecture（依存関係の方向制御）

アプリケーションの内部構造は Clean Architecture / Hexagonal Architecture に基づく。
核心は「依存関係の方向を制御する」こと。

```
Infrastructure → Application → Domain Model
    ↓                ↓              ↓
  外部技術         ユースケース    ビジネスルール
（HTTP, DB, Queue）
```

### 各層の責任

| 層 | 責任 | 依存先 | 外部ライブラリ |
|----|------|--------|---------------|
| Domain Model | エンティティ、ビジネスルール、インターフェース定義、エラー定義 | なし | 標準ライブラリのみ |
| Application | ユースケース実装、トランザクション境界、バリデーション | Domain Model のみ | 最小限 |
| Infrastructure | HTTP handler, DB実装, Queue consumer, 外部API連携 | Application + Domain Model | 自由 |

### 依存関係のルール

- 内側の層は外側の層を知らない。Domain Model は Infrastructure の存在を知らない
- 外側から内側への依存はインターフェースを通じて行う（Dependency Inversion）
- Application 層は他ドメインの Application 層の Service を DI で注入可能
- Domain Model 層にドメイン間の依存は書かない

## アーキテクチャ決定のフレームワーク

### 判断基準の優先順位

技術選定やアーキテクチャ決定で迷った時は、以下の優先順位で判断する:

1. 正確性（Correctness）— データの整合性、ビジネスルールの正しさ
2. 運用性（Operability）— デプロイ、監視、障害対応のしやすさ
3. 変更容易性（Modifiability）— 要件変更への対応コスト
4. パフォーマンス（Performance）— レイテンシ、スループット
5. コスト（Cost）— インフラ費用、開発工数

### ADR（Architecture Decision Record）

重要なアーキテクチャ決定は ADR として記録する。

```markdown
# ADR-{番号}: {タイトル}

## ステータス
Accepted / Proposed / Deprecated / Superseded by ADR-{番号}

## コンテキスト
なぜこの決定が必要になったか。背景と制約。

## 決定
何を決めたか。

## 理由
なぜその選択肢を選んだか。検討した代替案と比較。

## 結果
この決定によって生じる影響。トレードオフ。
```

- 「なぜそうしたか」を残す。コードは What を語るが、Why は ADR に書く
- 決定を覆す時は、元の ADR を Deprecated にして新しい ADR を書く

## 設定管理の原則

- 設定値はすべて環境変数から読み込む（Twelve-Factor App）
- シークレット（API キー、DB パスワード）はコードに含めない。Secret Manager / Vault を使う
- 環境ごとの差異は環境変数のみで吸収する。コードに `if production` を書かない
- デフォルト値は安全側に倒す（タイムアウトは短め、リトライは少なめ）

## セキュリティの原則

- ユーザー入力は常に信頼しない。バリデーション + サニタイズを徹底する
- 最小権限の原則。サービスアカウントには必要最小限の権限のみ付与する
- シークレットをログに出力しない。マスキングを徹底する
- 依存ライブラリの脆弱性を定期的にスキャンする（Dependabot, Snyk 等）
- HTTPS / TLS を必須とする。内部通信も暗号化する

## アーキテクチャのアンチパターン

- 分散モノリス: マイクロサービスに分割したが、サービス間の結合が強く、独立してデプロイできない
- 共有データベース: 複数サービスが同じ DB を直接参照する。スキーマ変更が全サービスに影響する
- 過度な抽象化: 将来の拡張のために不要なインターフェースや層を追加する（YAGNI 違反）
- 銀の弾丸思考: 1つの技術/パターンですべてを解決しようとする（マイクロサービス万能論等）
- ドキュメントなき決定: なぜその技術を選んだか、なぜその構成にしたかが記録されていない
