# System Design Patterns

具体的なシステム設計パターンの選択ガイド。
設計判断の哲学・原則は `architecture-philosophy.md` を参照。

## 通信パターンの選択フロー

設計時に最も頻出する判断「同期 vs 非同期 vs Job」を、以下のフローで決定する。

```
リクエストを受けた → レスポンスに結果が必要か？
  ├─ YES → レスポンスまでの許容時間は？
  │   ├─ 〜500ms → 同期処理（Sync Request-Response）
  │   └─ 500ms〜 → 同期だが内部で並行処理 or キャッシュ活用
  └─ NO → 処理のトリガーは？
      ├─ ユーザーアクション起因 → 非同期メッセージング（Async Event）
      ├─ 時間起因（定期実行） → Scheduled Job（Cron）
      └─ データ蓄積起因（バッチ） → Batch Job
```

### パターン別の特性

| パターン | レイテンシ | 結合度 | 信頼性 | 適用場面 |
|----------|-----------|--------|--------|----------|
| Sync Request-Response | 低 | 高 | 呼び出し先に依存 | CRUD、認証、バリデーション |
| Async Event（Fire-and-Forget） | - | 低 | Queue に依存 | 通知、ログ集約、検索インデックス更新 |
| Async Request-Reply | 中 | 中 | Queue に依存 | 長時間処理の結果通知 |
| Scheduled Job | - | 低 | スケジューラに依存 | レポート生成、データ集計、クリーンアップ |
| Batch Job | - | 低 | ジョブ管理に依存 | 大量データ処理、CSV インポート/エクスポート |
| Streaming | 継続的 | 中 | ブローカーに依存 | リアルタイムデータパイプライン |

### 具体的なシナリオ別パターン選択

| シナリオ | パターン | 理由 |
|----------|----------|------|
| ユーザー登録 | Sync | レスポンスで登録結果を即座に返す必要がある |
| ウェルカムメール送信 | Async Event | ユーザーは送信完了を待つ必要がない。失敗してもリトライ可能 |
| パスワードリセット | Sync + Async | トークン生成は Sync、メール送信は Async |
| 決済処理 | Sync | 結果を即座に返す必要がある。整合性が最重要 |
| 決済完了後の在庫更新 | Async Event | 決済成功イベントを購読して非同期で処理 |
| 月次レポート生成 | Scheduled Job | 定期実行。処理時間が長い |
| CSV 一括インポート | Batch Job | 大量データ。ユーザーは完了通知を後で受け取る |
| リアルタイム通知 | WebSocket + Async Event | サーバー→クライアントのプッシュ |
| 検索インデックス更新 | Async Event | データ変更イベントを購読して非同期で反映 |
| 画像リサイズ | Async Event | アップロード後に非同期で処理。結果は後で参照 |
| 日次データクリーンアップ | Scheduled Job | 期限切れデータの削除。定期実行 |
| 外部 API 連携（データ同期） | Scheduled Job or Async Event | ポーリング型なら Job、Webhook 型なら Event |

## 同期処理パターン

### Request-Response（HTTP / gRPC）

最もシンプルな通信パターン。以下の条件を満たす場合に使用する:

- クライアントがレスポンスを待つ必要がある
- 処理時間が短い（目安: 500ms 以内）
- 呼び出し先の可用性が十分に高い

#### タイムアウト設計

| 対象 | 推奨値 | 理由 |
|------|--------|------|
| HTTP クライアント全体 | 30s | 最大待ち時間の上限 |
| 個別リクエスト | 5〜10s | 通常の API 呼び出し |
| DB クエリ | 3〜5s | 長時間クエリの検出 |
| ヘルスチェック | 1〜2s | 素早い応答が必要 |

- タイムアウトは必ず設定する。デフォルト（無制限）のまま使わない
- 呼び出しチェーンでは、上流のタイムアウト > 下流のタイムアウトにする

## 非同期処理パターン

### Event-Driven（メッセージング）

サービス間の疎結合を実現する基本パターン。

#### 使用条件

- 処理結果をレスポンスに含める必要がない
- 処理の失敗をリトライで回復できる
- 処理順序の厳密な保証が不要（または Queue の機能で保証可能）

#### メッセージ設計

```json
{
  "id": "msg_abc123",
  "type": "user.created",
  "source": "user-api",
  "timestamp": "2025-01-15T09:30:00Z",
  "data": {
    "user_id": "usr_xyz",
    "email": "user@example.com"
  },
  "metadata": {
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "correlation_id": "req_abc123"
  }
}
```

- `id`: メッセージの一意識別子。冪等性チェックに使用
- `type`: ドメインイベント名。`{aggregate}.{event}` 形式
- `source`: 発行元サービス名
- `metadata.trace_id`: 分散トレーシングの Trace ID を伝播する

#### メッセージハンドラーパターン（Registry）

メッセージタイプに基づいてハンドラーをディスパッチする Registry パターンを使用する:

- メッセージタイプごとにハンドラーを実装し、Registry に登録する
- Registry が冪等性チェック・エラーハンドリングを共通化する
- 新しいメッセージタイプの追加は「ハンドラー実装 → Registry 登録」の2ステップ

### WebSocket（双方向リアルタイム通信）

サーバーからクライアントへのプッシュ通知が必要な場合に使用する。

#### 使用条件

- サーバー起因のイベントをクライアントにリアルタイムで通知する必要がある
- ポーリングではレイテンシ要件を満たせない
- 接続数が管理可能な範囲（数千〜数万）

#### Hub パターン

- Hub: すべての WebSocket 接続を管理する中央コンポーネント
- Client: 各接続を表現。送信チャネルを持つ
- readPump / writePump: 読み取り・書き込みを別 goroutine で管理
- Ping/Pong: 定期的な生存確認（推奨: 54秒間隔）

#### セキュリティ

- 本番環境ではトークンベースの認証を実装する
- オリジンチェック（CORS）を適切に設定する
- レート制限で過度なメッセージ送信を防ぐ
- クライアントからの入力は必ずバリデーションする

## Job / Batch パターン

### Scheduled Job（Cron）

定期的に実行する処理。

- 実行間隔は環境変数で設定可能にする
- 冪等性を担保する（同じ Job が2回実行されても結果が同じ）
- 実行ログ（開始時刻、終了時刻、処理件数、エラー件数）を記録する
- 長時間実行の場合はヘルスチェックを組み込む

### Batch Job（オンデマンド）

ユーザーリクエストやイベントをトリガーに大量データを処理する。

- 進捗状況を追跡可能にする（処理済み件数 / 全件数）
- チャンク単位で処理し、途中失敗時に再開可能にする
- メモリ使用量を制御する（全件ロードしない）
- 完了通知を非同期で送信する（メール、WebSocket 等）

## 冪等性（Idempotency）

分散システムではメッセージの重複配信が発生するため、冪等性の担保は必須。

### 冪等性チェックの基本フロー

```
メッセージ受信 → 冪等性キーで処理済みか確認
  ├─ 処理済み → スキップ（正常終了）
  └─ 未処理 → ステータスを "processing" に更新 → 処理実行
      ├─ 成功 → ステータスを "completed" に更新
      └─ 失敗 → ステータスを "failed" に更新（リトライ可能にする）
```

### 冪等性キーの生成戦略

| 戦略 | 用途 | 例 |
|------|------|-----|
| メッセージ ID | デフォルト。メッセージの一意性で十分な場合 | `msg.ID()` |
| ビジネスキー | 同じビジネスイベントの重複を防ぐ | `user.created:{user_id}:{email}` の SHA256 |
| リクエスト ID | 外部システムからの識別子 | `msg.Attributes()["request_id"]` |

### TTL（有効期限）

- 推奨値: 24時間〜7日
- 期限切れレコードは定期的にクリーンアップする
- TTL は処理のリトライ間隔を考慮して設定する

## リトライ戦略

### Exponential Backoff with Jitter

リトライ間隔を指数的に増加させ、ジッターで分散する。

```
retry_interval = min(base * 2^attempt + random_jitter, max_interval)
```

| パラメータ | 推奨値 | 説明 |
|-----------|--------|------|
| base | 1s | 初回リトライ間隔 |
| max_interval | 30s〜60s | 最大リトライ間隔 |
| max_retries | 3〜5 | 最大リトライ回数 |
| jitter | 0〜base | ランダムな揺らぎ |

### リトライ可否の判断

| エラー種別 | リトライ | 対応 |
|-----------|---------|------|
| 一時的エラー（5xx, タイムアウト, ネットワーク） | する | Exponential Backoff |
| クライアントエラー（4xx） | しない | エラーログ + DLQ |
| バリデーションエラー | しない | エラーログ + DLQ |
| リソース枯渇（429 Too Many Requests） | する | Retry-After ヘッダーに従う |

### Dead Letter Queue（DLQ）

リトライ上限を超えたメッセージは DLQ に送る:

- DLQ のメッセージは手動確認・再処理のフローを用意する
- DLQ にメッセージが入ったらアラートを発火する
- DLQ メッセージには元のメッセージ情報 + エラー理由を含める

## Circuit Breaker

外部サービスの障害が自サービスに波及するのを防ぐ。

### 状態遷移

```
Closed（正常）→ エラー率が閾値超過 → Open（遮断）
Open → 一定時間経過 → Half-Open（試行）
Half-Open → 成功 → Closed / 失敗 → Open
```

### パラメータ設計

| パラメータ | 推奨値 | 説明 |
|-----------|--------|------|
| failure_threshold | 5回 or 50% | Open に遷移するエラー閾値 |
| timeout | 30s〜60s | Open → Half-Open までの待機時間 |
| success_threshold | 3回 | Half-Open → Closed に戻る成功回数 |

### 適用箇所

- 外部 API 呼び出し
- 他マイクロサービスへの同期呼び出し
- DB 接続（接続プールの枯渇防止）

Circuit Breaker が Open の間は、フォールバック（キャッシュ返却、デフォルト値、エラーレスポンス）を返す。

## Saga パターン（分散トランザクション）

複数サービスにまたがるトランザクションを、ローカルトランザクションの連鎖で実現する。

### Choreography（イベント駆動型）

各サービスがイベントを発行し、次のサービスがそれを購読して処理する。

```
注文サービス → "order.created" → 在庫サービス → "stock.reserved" → 決済サービス
                                                                    ↓ 失敗
                                                              "payment.failed"
                                                                    ↓
                                              在庫サービス ← 補償: 在庫戻し
```

- サービス数が少ない（3〜4）場合に適する
- サービス間の結合が緩い
- フロー全体の可視性が低い（各サービスのログ/トレースで追う）

### Orchestration（オーケストレーター型）

中央のオーケストレーターが各サービスの呼び出し順序を制御する。

```
Orchestrator → 在庫サービス.Reserve()
             → 決済サービス.Charge()
             → 失敗時: 在庫サービス.Release()（補償）
```

- サービス数が多い、またはフローが複雑な場合に適する
- フロー全体の可視性が高い
- オーケストレーターが単一障害点になりうる

### 選択基準

| 条件 | Choreography | Orchestration |
|------|-------------|---------------|
| サービス数 | 少ない（2〜4） | 多い（5+） |
| フローの複雑さ | シンプル | 条件分岐が多い |
| 可視性の要求 | 低〜中 | 高 |
| 結合度 | 低い | オーケストレーターに集中 |

### 補償トランザクション

Saga の各ステップには対応する補償（ロールバック）処理を定義する:

- 補償処理も冪等にする
- 補償の失敗はアラート + 手動対応フローを用意する
- 補償の実行順序は元のトランザクションの逆順

## CQRS（Command Query Responsibility Segregation）

読み取りと書き込みのモデル/ストアを分離するパターン。

### 適用条件

- 読み取りと書き込みのスケーリング要件が大きく異なる
- 読み取り用に非正規化されたビューが必要
- イベントソーシングと組み合わせる場合

### 適用しない条件

- 単純な CRUD アプリケーション
- 読み書きの負荷が均等
- チームが小さく、複雑さのコストが見合わない

### 実装パターン

```
Command（書き込み）→ Write DB → Domain Event → Read Model 更新 → Read DB
Query（読み取り）→ Read DB
```

- Write DB: 正規化されたリレーショナル DB
- Read DB: 非正規化されたビュー（同じ DB の別テーブル、または別ストア）
- 結果整合性を許容する設計にする

## Queue / メッセージブローカー選定

| 基準 | SQS | NATS JetStream | Kafka |
|------|-----|----------------|-------|
| 運用コスト | 低（マネージド） | 中（自前運用） | 高（クラスタ管理） |
| スループット | 中 | 高 | 非常に高 |
| メッセージ順序 | FIFO Queue で保証 | Stream 内で保証 | Partition 内で保証 |
| メッセージ保持 | 最大14日 | 設定可能 | 設定可能（長期保持向き） |
| Consumer Group | なし（Worker パターン） | あり | あり |
| 再処理 | DLQ から手動 | Replay 可能 | Offset リセットで可能 |
| AWS 統合 | ネイティブ | なし | MSK あり |

### 選択ガイド

- SQS: AWS 環境でシンプルなタスクキューが必要な場合。運用負荷を最小化したい
- NATS JetStream: 低レイテンシ + 軽量な Pub/Sub が必要。マイクロサービス間の内部通信
- Kafka: 大量データのストリーミング、イベントログの長期保持、複数 Consumer による再処理が必要

### Queue 共通ルール

- すべての Queue Consumer で冪等性チェックを実装する（At-Least-Once 配信が前提）
- メッセージハンドラーは Registry パターンで統一する
- Graceful Shutdown: 処理中のメッセージ完了を待ってから停止する
- DLQ を設定し、リトライ上限超過メッセージを退避する

#### SQS 固有

- Long Polling（`WaitTimeSeconds > 0`）を使用して API コール数を削減する
- Visibility Timeout を処理時間に合わせて設定する
- 処理成功時のみ `DeleteMessage` を呼ぶ

#### NATS JetStream 固有

- Core NATS ではなく JetStream を使用して永続化を確保する
- `AckPolicy: AckExplicit` を使用する
- 処理成功: `msg.Ack()`、リトライ可能な失敗: `msg.Nak()`、リトライ不可: `msg.Term()`
- Durable Consumer を設定して再起動時に処理状況を引き継ぐ

#### Kafka 固有

- Consumer Group ID を必ず設定する
- Start Offset は環境変数で設定可能にする（デフォルト: `FirstOffset`）
- 明示的なオフセットコミットを推奨（自動コミットは処理前コミットのリスクあり）
- `MinBytes` / `MaxBytes` でバッチ受信を最適化する

## DB 選定ガイド

| 要件 | PostgreSQL | DynamoDB | Redis | Elasticsearch |
|------|-----------|----------|-------|---------------|
| トランザクション | ACID 完全対応 | 制限あり | なし | なし |
| スキーマ | 固定（マイグレーション） | スキーマレス | Key-Value | スキーマレス |
| スケーリング | 垂直 + Read Replica | 水平（自動） | 水平（Cluster） | 水平（Shard） |
| クエリの柔軟性 | 高（SQL） | 低（PK/SK） | 低（Key ベース） | 高（全文検索） |
| 適用場面 | メインデータストア | 高スループット KV | キャッシュ、セッション | 検索、ログ分析 |

- デフォルトは PostgreSQL。理由が明確でない限り他を選ばない
- キャッシュ層として Redis を追加するのは有効
- 全文検索が必要な場合に Elasticsearch を追加する
- DynamoDB は高スループット + シンプルなアクセスパターンの場合のみ

## API 設計

### RESTful API

- リソース指向の URL 設計（`/api/v1/users/{id}`）
- HTTP メソッドを正しく使い分ける（GET: 取得、POST: 作成、PUT: 全体更新、PATCH: 部分更新、DELETE: 削除）
- エラーレスポンスは RFC 7807 Problem Details に準拠する
- バージョニングは URL パス（`/api/v1/`）で行う
- リスト API にはページネーション（`limit` / `offset` or カーソル）を必須とする

### API 間通信

- サービス間の同期通信は gRPC を優先する（型安全、高速）
- 外部公開 API は REST（JSON）を使用する
- API Gateway でレート制限・認証を一元管理する

## Graceful Shutdown

すべてのサーバー/ワーカーは Graceful Shutdown を実装する。

### 共通インターフェース

```
Application interface:
  Run(ctx) error      — メインループ。ctx.Done() を監視して終了
  Shutdown(ctx) error — リソース解放。処理中リクエストの完了待機
```

### シャットダウンシーケンス

```
SIGTERM 受信 → 新規リクエスト受付停止 → 処理中リクエスト完了待機 → リソース解放 → 終了
```

- シャットダウンタイムアウトを設定する（推奨: 30秒）
- タイムアウト超過時は強制終了する
- ヘルスチェックエンドポイントを即座に unhealthy にする（ロードバランサーからの切り離し）

### コンポーネント別の注意点

| コンポーネント | シャットダウン時の処理 |
|---------------|---------------------|
| HTTP Server | 処理中リクエストの完了を待機 |
| Queue Consumer | 処理中メッセージの完了を待機。新規メッセージ受信を停止 |
| WebSocket Hub | 全クライアント接続を Close |
| DB Connection Pool | アクティブクエリの完了を待機してプールを Close |
| Scheduled Job | 実行中ジョブの完了を待機 |

## マイグレーション戦略

### DB マイグレーション

- マイグレーションツール（`golang-migrate`, `tern`, `Flyway` 等）を使用する
- マイグレーションファイルはバージョン管理する
- 破壊的変更（カラム削除、型変更）は段階的に行う:
  1. 新カラム追加 → 2. アプリケーション更新 → 3. データ移行 → 4. 旧カラム削除
- ロールバック可能なマイグレーションを書く

### サービスマイグレーション

- Blue-Green デプロイまたは Canary デプロイを使用する
- 後方互換性を維持する（新旧バージョンが同時に動作できる）
- Feature Flag で段階的にリリースする

## アンチパターン

- 同期の連鎖: A → B → C → D と同期呼び出しが連鎖する。1つの障害で全体が止まる
- 非同期の乱用: すべてを非同期にして結果整合性の複雑さに溺れる
- Queue を DB 代わりに使う: Queue はメッセージの一時的な受け渡し。永続データストアではない
- リトライなしの外部呼び出し: ネットワークは信頼できない。一時的エラーにはリトライする
- タイムアウトなしの同期呼び出し: 呼び出し先の障害で自サービスがハングする
- 冪等性なしの非同期処理: 重複配信でデータ不整合が発生する
- 補償なしの分散トランザクション: 途中で失敗した時にデータが中途半端な状態で残る
